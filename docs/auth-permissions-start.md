# Личный кабинет и система permissions (frontend-only) — стартовый план

## Цель
Собрать базовый ЛК и проверку прав без сервера, с минимальными изменениями текущего проекта.

## Ограничение
Без backend это только UX-ограничение (скрытие UI и guard'ы).  
Это не полноценная защита: права можно подменить через DevTools.

---

## Порядок внедрения (без большого рефакторинга)

### Шаг 1. Типы ролей и прав
Создать файл: `src/entities/auth/model/types.ts`

Что определить:
- `Role` (например: `guest | user | admin`)
- `Permission` (например: `view_main | view_cabinet | edit_profile | create_user`)

Зачем:
- Единая типобезопасная основа для всей системы доступа.

---

### Шаг 2. Матрица прав role -> permissions
Создать файл: `src/entities/auth/model/permissions.ts`

Что добавить:
- Объект сопоставления ролей и прав.
- Функцию `getPermissionsByRole(role)`.

Зачем:
- Вся логика доступа в одном месте.
- Позже легко заменить источник прав (например, с сервера).

---

### Шаг 3. AuthContext (отдельно от UsersContext)
Создать файл: `src/entities/auth/model/AuthContext.tsx`

Минимум в контексте:
- `currentUser`
- `permissions`
- `loginAs(role)` (временный для демо)
- `logout()`
- `can(permission)`

Важно:
- `UsersContext` не менять, не смешивать ответственность.
- `AuthContext` отвечает только за “кто пользователь” и “что ему можно”.

---

### Шаг 4. Подключение провайдера в корне
Подключить `AuthProvider` в корневом входе приложения (`App`/`main`), рядом с `UsersProvider`.

Рекомендуемая вложенность:
- `AuthProvider`
  - `UsersProvider`
    - `App/Pages`

---

### Шаг 5. Guard-компоненты
Создать:
- `RequireAuth`
- `RequirePermission`

Применять точечно:
- Защита страницы ЛК.
- Защита действий/блоков интерфейса.

---

### Шаг 6. Первое внедрение в UI (минимум)
На старте внедрить только в 1–2 местах:
1. На `MainPage` показывать кнопку `Add New User` только при `can("create_user")`.
2. Сделать страницу ЛК и обернуть ее в `RequirePermission("view_cabinet")`.

---

### Шаг 7. Dev-переключатель ролей
Добавить временный переключатель роли (guest/user/admin) для локальной проверки сценариев.

Зачем:
- Быстро тестировать доступы без сервера и без сложной auth-инфраструктуры.

---

## Как связать с текущей структурой

- `UsersContext` — данные пользователей (списки/фильтры/пагинация).
- `AuthContext` — текущий пользователь и permissions.
- В компонентах использовать оба:
  - `useUsers()` для данных
  - `useAuth()` для проверки `can(...)`

Связь только в UI-условиях, без смешивания стейтов.

---

## Чтобы безболезненно перейти на сервер позже

1. Не хардкодить роли в компонентах (`if role === 'admin'`), использовать только `can(...)`.
2. Держать матрицу прав централизованно (`permissions.ts`).
3. Не завязывать `AuthContext` на внутренности `UsersContext`.

Тогда при переходе на backend вы замените только источник `currentUser/permissions`, а UI почти не придется переписывать.
